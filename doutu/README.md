# Doutu Android App

Native Android app written in Java. The main shell draws the four service pages on a fixed reference canvas and routes the “微” page into a separate, interactive WeChat-style activity.

## Project structure

- `app/src/main/java/com/luoyun/doutu/MainActivity.java` — main shell, service-page artwork, feature list, and bottom navigation. It also owns three behaviours added on 2026-10-16: the **launcher landing page** — `routeLauncherEntry()` runs at the end of `onCreate` and starts the 微信 / 支付宝 pages immediately, so the app home never paints a frame (waiting for the version check first was what made the home flash for a few hundred ms; when an update does turn up later, `bringShellToFrontForUpdate()` pops the internal page with `CLEAR_TOP` so the dialog is actually visible); the **分享好友 / 邀请好友** action on the 微 grid and the 我 page (copies `Session.shareLink()` and shows `Session.shareTip()`, both backend-configurable); and the gap above the bottom bar — the 首页 paints `#f6f6f6` from y **2142** (the four reference images turn pure white at y=2145, so anything later left a thin white line) and the 娱乐 page no longer paints a white footer block. The 娱乐 page's rows are wired the same way as the 微 grid's tiles: **模拟朋友来电** goes through `openWeiCall()` into the 模拟来电设置页 (see the `features/call/` entry below) — the same page the 微 page's 模拟来电 tile opens, with no membership gate on either side — and 短视频一键去水印 goes through `openParseWithGate()` like the 微 page's 抖音去水印 tile.
- **No more 「XX · 演示功能」 popups (2026-10-16).** Every spot that is not implemented yet is now a silent no-op instead of answering with a placeholder toast — 199 sites in all. The canvas pages (`*Screen.java`) keep the hit region but return `"noop"` where they used to return `"toast:XXX · 演示功能"` (replacing the token, not deleting the `hit(...)`/`return`, matters: a removed region would let the tap fall through to whatever is registered behind it), and the activities drop the statement outright (`toast("…")` / `Toast.makeText(…)`), leaving the surrounding `break` / `return` intact. `_ops/drop_demo_toasts.py` is the transform that did it and prints a per-file report; a tap on one of these spots must leave the screen pixel-identical, which `_ops/no_toast_check.py` asserts (it masks the status-bar clock and the 首页 rolling banner).
- `app/src/main/java/com/luoyun/doutu/features/call/` — **模拟来电 is now a setup page + a scheduled call (2026-10-16).** Both entries (微 → 模拟来电 and 娱乐 → 模拟朋友来电) open `CallSetupActivity` instead of starting a call outright, and that page decides四件事: 来电人（`CallContacts` 里的通讯录横排，点一个名字和头像一起选上）, 头像与名称（头像可单独从相册换，名字随便改）, 铃声（内置那首，或者从手机里挑一个音频文件）, 什么时候响（立即 / N 分钟后 / 指定钟点）. Everything is remembered per account in `CallStore` (which also self-heals: a remembered avatar or ringtone whose file is gone falls back to the contact's picture / the built-in ring instead of playing nothing, and picking 默认铃声 deletes the copied file), avatars and ringtones are copied into `filesDir/call_assets/` — the file names carry the account suffix, and `Accounts` deletes them with the account — and the WebView serves them back to the page under `https://fake-world.local/__call_assets/…`, so the call screen itself is unchanged — `WeiHomeActivity` hands `{name, avatar, ringtone}` to a new page hook `window.__fwOpenCall`, which mounts the very same 来电界面 with `call.contact` and the ring set to the user's choices. 到点响走 `CallScheduler`: an exact alarm into `CallAlarmReceiver`, which (a) tries to open the call screen and (b) posts a full-screen-intent notification as the fallback for ROMs that block background activity starts. Two real-device findings are baked in: `setAlarmClock` needs `USE_EXACT_ALARM`/`SCHEDULE_EXACT_ALARM` (without them the system throws `SecurityException`, and a fallback call inside the catch block once crashed the app), and the contacts' own avatar URLs point at a `cdn-fakeworld.azureedge.net` that no longer resolves, so `CallImages` maps each contact to one of the bundled `user-avatar-*.jpg` instead.
- `app/src/main/java/com/luoyun/doutu/features/sound/` — **模拟收款声音 (2026-10-16)**, the 娱乐 page's third 社恐神器 row (the original app's `/account_sound`, displayed as 支付宝到账声音). It is a **local TTS splicer**: an amount is read out of `assets/audio/account_sound/` — the 20 mp3s copied byte-for-byte out of the reference pack (`00_资料包`, SHA-256 verified) are digits 0-9 plus 点/十/百/千/万/亿. The order is **固定录音在前、拼出来的金额在后** (`diaoluo_da.mp3` 到账提示音 → `tts_success.mp3` / `tts_wxsuccess.mp3` 「支付宝到账」/「微信支付收款」 → 逐字拼的金额 → `tts_yuan.mp3` 「元」), i.e. 叮·支付宝到账·88 元; the reference pack's prose calls the two fixed lines 尾音, but playing them last gave "88 元，支付宝到账", which is backwards — the real announcement leads with them. `SoundScript` turns the amount into that clip list and is deliberately **pure Java with a `main()`** — `java SoundScript.java` prints a table of amounts (`88 → 叮·支付宝到账·8十8·元`, `15 → 十5`, `1001 → 1千零1`, `100000 → 十万`, `0.01 → 零点零1`) so the Chinese-number reading and the clip order can be checked on the desktop instead of by ear on a phone. `AccountSoundPlayer` plays the list with **`setNextMediaPlayer` hand-off rather than a per-clip completion callback** — the callback path waits for the player to drain and for a message to come back on the main thread, which put a hundred-odd milliseconds of silence between every digit; the platform-to-platform hand-off is seamless, and the on-completion chain survives only as a fallback. On top of that sit the original's switches: 小支/小微 收款, 随机收款方, 播报一次 / 循环播报 / 无限收款模式, 随机金额区间 (10-100 / 100-1000 / 1000-10000), 延时播放 (2/5/10 s) and 倍速 0.5-1.5, all remembered per account in `SoundStore`. The page itself was re-laid-out in this round: a summary line at the top says what the next call will sound like, the amount box and its button share one row, each block is a card with its title inside it, and the mode/延时/倍速 choices are chip rows.
- `app/src/main/java/com/luoyun/doutu/features/shutdown/ShutdownActivity.java` — **模拟没电关机 (2026-10-16)**, the 娱乐 page's 社恐神器 row 2 (the original app's `/shutdown`, displayed as 模拟关机). This one is written from the inverse-engineering findings rather than from a screenshot, and the findings are worth stating exactly: the reference pack confirms the entry, the i18n key `more_playing.shutdown` = 模拟没电关机, the Remix glyph `U+F116` and the route `/shutdown → Pcb (class id 3823)` — and proves the page loads **zero resources**, touches **zero tables** and makes **no requests**, while the page class `Pcb` has no declaration at all in the decompiler output (560 of 881 classes are like that), so its widget tree is genuinely unavailable. What follows from zero resources is that the page must be a **pure code-drawn full-screen picture**, i.e. a black screen; the pack's two leads point the same way (the package bundles `wakelock_plus`, and the whole package contains exactly one `SystemChrome.setEnabledSystemUIMode(SystemUiMode.manual)`). So the page is: black full-screen + `FLAG_KEEP_SCREEN_ON` + status and navigation bars hidden (re-hidden on every focus change, the sticky-immersive dance done by hand for API 30+ and with the legacy flags below it), tapping anywhere or pressing back returns to the app. In the middle sits the **没电的电池**, drawn on the canvas in the same Path style as the 娱乐 page's own icons and pulsing slowly (alpha 0.10 → 0.80, 1.5 s each way) — it is drawn rather than shipped as an image because there *is* no such asset anywhere: all 118 glyphs of the reference pack's Remix subset were rendered to a sheet and it only has `U+F116`, a **filled battery with a lightning bolt** (the 娱乐 row's own entry icon, i.e. charging), and a sweep of our `res/drawable-nodpi` and `assets/` turns up no battery/power file at all. An empty outline reads as 没电, needs no resource, and stays sharp at any density. For the first 2.4 s a very dark 点一下屏幕回到豆图 line sits at the bottom so nobody thinks the phone actually died; then it goes and what is left is black with the battery blinking in the middle. **What is not known:** whether the original draws a battery at all (or a black screen, or something else) and whether it hides the system bars — the pack marks both as unconfirmed, and so does this implementation.
- `app/src/main/java/com/luoyun/doutu/features/order/` — **淘宝订单详情 (2026-10-17)**, the 娱乐 page's 实用功能 row 2. Unlike the other feature pages this one is **reproduced pixel-for-pixel from two screenshots the user supplied** (a 1380-wide full screen and a 970-wide long capture), and the numbers in `TaobaoOrderActivity` are the reference picture's own pixels: everything is placed in a 1380-unit design space and multiplied by `k = screenWidth / 1380` at runtime, `y` values are the reference's **absolute screen** coordinates, and text is dropped by **ink centre** (`setIncludeFontPadding(false)` makes the ink centre sit at `top + 0.5 × font size`). Nothing here is estimated: card edges, radii, hairlines, every line's position and size came out of `_ops/measure_order_ref.py` + `_ops/probe_order_ref.py`, and each font size was then **calibrated by comparing the ink width of the same string in both pictures** (`_ops/elcomp.py`, a `_ops/diff_order.py` band report drives the loop) until the width ratio sat within a few percent. No icon is hand-drawn either — the back arrow, the three dots, the location pin, ⓘ, the 客服 bubble, the red 购物券 badge, the Apple logo block, the up/down carets and the right chevron are all **cut out of the reference pictures** by `_ops/cut_order_icons.py`, which unpremultiplies each icon off its white background into a transparent PNG; the product photo and the six recommendation tiles are cropped out of the same pictures. **Every field on the page is tappable and editable** (tap a value → an input dialog; tap the product photo → the system picker, or 恢复参考图), and all of it persists per account in `OrderStore` alongside the other stores, so killing the app does not lose an edit. On first open the private fields (收货人 / 手机号 / 地址 / 订单号 / 支付宝交易号 / 创建时间 / 成交时间) are **randomised on the spot** — none of the user's real information is seeded — while 店铺 / 商品 / 金额 / 推荐位 start from the reference picture. Three deliberate departures from the reference, all at the user's request: the title is 交易成功 (and is itself editable, stored under `order_title`), the 其他 subtitle is gone and the title sits lower, and the bottom bar no longer has 删除订单 (it is 客服 on the left, 加入购物车 on the right). The ⋯ in the corner is decoration only — it has no click handler.
- `app/src/main/java/com/luoyun/doutu/features/service/CustomerServiceActivity.java` — **人工客服 (2026-10-17)**, opened from 我 → 人工客服. One page, three things, **all three managed on the server** so they can be changed without shipping an app: the line above the QR code (`cs_notice`, default 开通会员、不会使用等问题均可询问客服), the QR image in the middle (`cs_qr_image`, any http(s) address — an empty value shows 二维码待后台配置 instead of a blank square), and the phone number / WeChat id below it (`cs_contact`), which the user can **tap to copy** (the clipboard write is confirmed both by a toast and by the 点击复制 caption turning into 已复制 ✓). The backend ships them in `/api/v1/config` under `customer_service`, `Session.applyCustomerService` persists them so the page paints instantly from the last known values, and the page re-fetches on open so a change made in the admin panel shows up on the next visit. In the admin UI they live in the 全局配置 page under a 客服 group named 客服页顶部文案 / 客服联系方式 / 客服二维码图片地址.
- `app/src/main/java/com/luoyun/doutu/features/play/PlayStore.java` — the 娱乐 page's switches, per account. There is one: **撩妹加V** (娱乐 → 乐趣挑逗). Turning it on means "this phone's camera is broken": in the 微 module, 小微主页 → 加号 → 扫一扫 then only pops 摄像头不可用 / 检测到摄像头硬件损坏，扫一扫功能暂时无法使用 and **never reaches the 付款给个人 page it used to open** (`wechat-chat-actions.js`, `openFeature('扫一扫')` asks the native side through the `DoutuApp.isScanDisabled()` bridge method first). Turning the switch back off restores the old behaviour exactly. The switch state is persisted, so it survives a cold start, and it is wiped with the account like every other store.
- `app/src/main/java/com/luoyun/doutu/TermsActivity.java` — the launcher entry (`用户须知与免责声明`, scroll-to-bottom + 5s before 同意 is enabled). All four launcher `activity-alias`es point at it, so `getIntent().getComponent()` tells it **which icon the user tapped**: 支付宝 / 支付宝（香港） → 小支主页, 微信 → 小微主页, 豆图 / 其它 → 应用主页. It starts `MainActivity` with `FLAG_ACTIVITY_CLEAR_TOP | FLAG_ACTIVITY_SINGLE_TOP` and passes the landing marker.
- `app/src/main/java/com/luoyun/doutu/features/feedback/FeedbackActivity.java` — 意见反馈 / 求新功能, opened from 我 → 求新功能. Up to three pictures through the system picker (each decoded, scaled to 1280 px, JPEG-compressed to ≤ 350 KB and uploaded as a `data:` URL), a 1000-character suggestion box with a counter, an optional contact field, and a thank-you dialog on success. Submissions land in the backend's 意见反馈 menu (see `server/docs/API.md` 6.7).
- 我 → 常用服务 四行的去向 (2026-10-17): 人工客服 opens `features/service/CustomerServiceActivity`; 求新功能 opens the feedback page; 邀请好友 copies the share link; **更多设置 is not built yet and only raises a 待更新 toast** — it no longer opens the placeholder detail page, which is the same rule the 娱乐 page already follows (no 「XX.演示功能」 popups, and unmapped rows either do the real thing or stay silent).
- `app/src/main/java/com/luoyun/doutu/account/UpdatePrompt.java` — **版本推送的客户端落点 (2026-10-17 重做)**. The logic used to live inside `MainActivity` and ran **once in `onCreate`**, which produced the exact bug the operator reported as 「服务端推送版本在客户端不起作用」:
  1. publish a version while the app is installed, switch back to the app from the background → **no dialog**; it only appeared after killing the process and starting over;
  2. worse, when the launcher icon is 微信/支付宝 the app immediately stacks 小微主页 / 小支主页 on top, so the activity that receives `onResume` is that page and `MainActivity` never wakes up at all.
  It is now a global singleton driven from `DoutuApp`'s `ActivityLifecycleCallbacks` — the same mount point as the watermark, for the same reason (20+ activities; touching them one by one guarantees a miss). Every page re-checks on resume, throttled to **60 s**, and the dialog is shown on **whichever activity is actually in front**, which also removes the old `bringShellToFrontForUpdate()` hack (CLEAR_TOP-ping the shell because the dialog was attached to a window nobody could see). 「稍后再说」 suppresses re-prompting for the rest of the run only — a cold start checks again. A forced update keeps `isForced()` true so `MainActivity`'s back key / landing-page jump still stand down. Verified on device three ways: cold start, warm resume on `MainActivity`, and warm resume while the 人工客服 page was on top (the case that was completely dead before).
- 服务端 `version/check` 同期修的三处 (`server/src/modules/config/routes.js`): 客户端**不带渠道**时不再按渠道过滤（以前运营在「高级设置 → 渠道」里随手填一个词，这个版本就谁都收不到）；`gray_percent` 从「存了没人用」变成真的按 `device_id` 哈希灰度，且强制更新不吃灰度；响应带 `reason`（`has_update` / `no_newer_release` / `gray_miss`）说明这次为什么推或不推。后台保存版本时也会提示「版本号没比已发布的更大」「渠道不是 all」这两种「发布了但收不到」的情况。回归：`server/scripts/version-check-test.js`（23 项）。
- 去水印的进度与耗时 (2026-10-17，抖音「进度条卡在 45%」之后的四刀):
  1. **服务端把「合成中」提前到解析一结束** (`taskService.processTask`). 客户端的状态映射是 排队 15% / 解析 45% / 合成 80% / 完成 100%，而下载原片原先发生在「解析中」这一段里：抖音原片下得慢时，进度条就会几分钟钉在 45%。现在解析一完就切 status 2，45% 这一档只剩解析本身（实测 5 秒），慢的部分落在 80% 上 —— 至少它在动。
  2. **下载改成流式落盘 + 按「多久没数据」判死** (`storage.downloadToTemp`). 以前是 `arrayBuffer()` 整个读进内存再写盘，而且只看总时长：抖音 CDN 偶尔直接卡住不动，要占满 120 秒才 abort —— worker 并发只有 2，一条卡住的任务会把整个队列堵死（生产日志里能看到后面排队的任务等了 53–126 秒）。现在边收边写，**20 秒没收到数据就失败**，卡住的任务立刻释放；总时长放宽到 180 秒，因为慢但一直在动的下载不该被杀。
  3. **备用地址 + 平台 Referer**. 抖音一次解析会给 `video_list`（同一段视频的多个 CDN 地址），以前只用第一条，第一条不通就整条任务失败；现在挨个试。Referer 也不再一律用直链自己的域名：抖音 CDN 上同一段视频，带 `https://www.douyin.com/` 比带自己域名**快约 7 倍**（实测 674ms vs 4551ms）。
  4. **客户端轮询不再一失败就永久停** (`ParseActivity.poll`). 以前只要有一次查询失败就 `polling = false`，网络抖一下进度条就永远钉在原地 —— 这本身就是「卡住不动」的一个来源。现在连续失败 5 次才放弃（中间 2 秒重试一次），并加了 8 分钟总时长兜底。
  真机实测（娱乐 → 短视频一键去水印，抖音链接）：提交 → 45%（约 6 秒）→ 100% 出结果，全程约 9 秒。
- **聊天时间分割线：间隔不足 3 分钟不显示 (2026-10-17)**: 小微主页里画会话的 `drawMessages()` 原来判断的是「这条消息的 HH:MM 跟上一枚时间戳的字符串是否相同」，等于**分钟一变就插一条时间** —— 连着聊十句能插出七八个时间。现在改成微信那套：拿 `message.createdAt` 跟上一条消息比，**间隔 ≥ `TIME_GAP_MS`（3 分钟）才插新的时间**（`wechat-chat-actions.js`，想改成 5 分钟只动这一个常量）。两个边界也顺手兜住了：第一条消息（没有可比较对象）照常显示时间；历史时间戳倒着排时（`gap < 0`，批量生成的会话会出现）也当作新一段，免得把时间吞掉。没有 `createdAt` 的消息不再清空比较基准 —— 它们本来就不参与计时。真机实测：第一条显示 `18:06`，3 分钟内再发不显示，隔 4 分钟后发显示 `18:10`。
- **本地头像已全部删除 (2026-10-17)**: `app/src/main/assets/fake_world/assets/generated-avatars/` (402 个文件、2.66MB —— 200 个 DiceBear SVG + 200 个 JPG) 整体删掉，**头像一律走 随机头像 API** (`v2.xxapi.cn/api/head`，`wechat-chat-actions.js` 的 `apiAvatarFor`，按 seed 稳定 + 首次成功后被原生化缓存冻结成本地文件)。这批图片原本只剩下两个用途：① 约 20 处 `onerror` 的兜底头像；② 群成员 / 随机生成联系人的头像池。现在前者换成 `bundledAvatarFor()` 返回的**内联 SVG 占位图**（`PLACEHOLDER_AVATAR`，几十字节、永远不会加载失败，比裂图体面），后者换成 `avatarUrl(index) => apiAvatarFor('member-' + index)`，`wechat-pay-pages.js` 的账单头像同理。同时**刻意保留**了 `migrateBundledAvatars()` 里那个 `/^\.\/assets\/generated-avatars\//` 正则 —— 老用户本地存的状态里还写着这些路径，留着它才能把旧头像就地迁到 API，否则升级上来就是一片裂图。APK 因此小 1.8MB（39.8MB → 37.9MB）。附带删掉的死代码：`BATCH_PHOTO_IDS`（`makeBatchAvatarUrl` 里算了却没用）、`BUNDLED_AVATAR_FILES`、`BILL_AVATAR_COUNT`。
- **DTW/1 私有协议（2026-10-17，1.0.0 起）**: `account/dtw/` 三个类 —— `DtwCrypto`（原语）、`DtwSession`（握手 + 会话状态）、`DtwTransport`（组帧/拆帧 + 隧道 HTTP）。**客户端不再携带服务端 `MASTER_KEY`**（以前编译在 `BuildConfig` 里，反编译就能伪造官方客户端、铸造成品下载签名、推导会话密钥），只留**服务端公钥**与慢哈希盐 —— 都是可公开材料。所有接口封成 AES-256-GCM 帧 POST 到 `/api/v1/dtw`，业务签名（会话接口的 sign_key）照旧算，只是塞进加密载荷的 `h` 字段；`rb` 必须带**签名时那个原始 JSON 串**，否则服务端重新 stringify 后键序一变就验签失败。三个踩过的坑写在 `DtwCrypto` 的注释里：① `PBKDF2WithHmacSHA256` 要 API 26，minSdk 24 → 手写 PBKDF2（已与 Node 逐字节对齐验证）；② Android 的 `RSA/ECB/OAEPWithSHA-256AndMGF1Padding` **MGF1 默认是 SHA-1**，必须显式传 `OAEPParameterSpec`，否则和 Node 的 `oaepHash:'sha256'` 对不上；③ 服务端的 `kid` 是字符串，客户端按 int 取会变成 0，转录串一拼就验签失败。打包新增两个参数：`-PdtwPublicKeyFile=<公钥.pem> -PdtwSalt=<服务端 DTW_SALT>`（多行 PEM 走 `-PdtwPublicKey` 容易被 shell 打散，所以支持从文件读）。协议文档见 `server/docs/DTW-PROTOCOL.md`。

## Build

Install Android SDK platform 35 and configure its location in the untracked `local.properties` file, for example:

```properties
sdk.dir=D:/and_sdk
```

Build the debug APK with:

```powershell
.\gradlew.bat :app:assembleDebug
```

The output is `app/build/outputs/apk/debug/app-debug.apk`. Build outputs and machine-specific SDK paths are generated/local files and should not be manually moved into the source tree.

## UI checks to run before shipping

### Coordinate-space check (`tools/check-ui-coords.py`)

Every canvas screen draws in a fixed **design space** (1080x2388, or the per-screen `Screen.W`/`Screen.H`
constants) and the view scales it to the real display. Touch handling must therefore convert the event
position into that same design space **before** any comparison:

```java
float rawX = e.getX() * W / getWidth();   // screen -> design, correct
float rawY = e.getY() * H / getHeight();
```

Mixing the two spaces silently "works" on any device whose resolution happens to equal the design
space and then breaks on every other device. That is exactly what happened with the bottom tab bar:
`rawY >= 2212f * getHeight() / H` was true on a 1080x2388 phone and false forever on a
1440x3168 phone, so tapping 首页/娱乐 from the 我 page did nothing there.

Run the checker after touching any touch-handling code:

```powershell
python tools\check-ui-coords.py     # exit 0 = clean, 1 = suspicious mixing found
```

It scans every `onTouchEvent` / `dispatchTouchEvent` body and flags screen-size calls
(`getWidth()`, `getHeight()`, `getDisplayMetrics()`, `widthPixels`) that are not the sanctioned
"screen -> design" division. It is a heuristic: it catches the shapes we have seen, not every possible
way to mix spaces, so also verify by hand on at least two display geometries.

### Multi-resolution smoke test

Because this class of bug only shows up at other geometries, verify the tab bar on several sizes
before releasing — `adb shell wm size WxH` re-lays out the app at a new resolution, `wm size reset`
restores the device:

```powershell
adb shell wm size 720x1600   ; adb shell wm size 1440x3168   ; adb shell wm size 1200x2000
# tap 我 in the bottom bar, then 首页 — the page must change on every size
adb shell wm size reset
```

Checked so far (tab bar works on all of them): 1080x2388, 1440x3168, 720x1600, 1080x2400, 1200x2000,
1440x2560, plus `wm density` 320/720 and system `font_scale` 1.5.

### Click sweep (`_ops/ui_sweep.py`, repo root level)

Walks a fixed route of taps (home tabs, the 支 grid, the 娱乐 entries, the 我 entries) at several
resolutions, and after every tap asserts that the process is still alive and that logcat has no new
`FATAL EXCEPTION`. It finishes with the navigation invariant — from the 我 page, tapping 首页 must
really change the screen — and prints PASS/FAIL per resolution, resetting `wm size` afterwards.

```powershell
python D:\AAA\doutu\_ops\ui_sweep.py <device> --sizes 1080x2388,1440x3168,720x1600,1200x2000
```

Coordinates in that script are written in the 1080x2388 design space and converted per resolution, so
it exercises the same mapping the app uses. It has a guard that aborts/relaunches when the foreground
window is no longer this app — without it, a step that leaves the app makes the later nav check report
a bogus failure.
